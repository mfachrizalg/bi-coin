Abstract—With the evolution of Internet Technology, payment
methods have undergone drastic changes from entity exchange
to Internet banking. Almost every sector has gone through
the transformation from conventional technologies to digital
technologies. With the arrival of online payment and digital
wallet system, making payments has become easier than ever
and with the increasing demand for such services, the number of
users using instant money transfer systems are growing rapidly.
However, the existing online payment system has issues like a
single point of failure, transparency, and insider problem. Also,
security in such online payments is crucial to mitigate risks and
financial inefficiencies. In this paper, a private and permissioned
Blockchain-based Payment System for the financial sector in
India is proposed. The proposed architecture is based on Istanbul
Byzantine Fault Tolerance (IBFT) consensus and it also discusses
the integration of banks with the system.
Index Terms—Blockchain, Online payment system, Consensus,
Digital wallet, IBFT

I. I NTRODUCTION
With the evolution of the Internet technology, payment
methods have undergone drastic changes from entity exchange
to Internet banking. Digital payments have evolved at an
exponential rate in the 21st century. Not only in the private sectors, even Governments of various countries are taking many
initiatives to encourage digital payments in their countries.
With blockchain as the underlying technology, virtual currency has gained a lot of popularity in recent years and many
sectors will be adopting these technologies. There are various
cryptocurrencies already in this field and when it comes to
adoption of such technology to financial and banking sectors
integrity of transactions and computation of validation in
such systems is crucial. As these are mostly permissionless,
applications based on blockchain should carefully address
the above issues or at least should maintain a good trade

A. Limitations of Current Online Payment Systems
Current online payment systems have some limitations.
Though the government would launch the digital payment
system, it would always have insider problem, i.e. anyone
in the organization with access to the central database can
manipulate the data. This data can be user account details,
account balance, transaction data, or the system data itself.
There is always a dependency on authenticated administrators,
which can be a risk for such government initiatives. Also,
there is always a risk of a single point of failure in current
payment systems. The Reserve Bank of India (RBI) also
considers this problem as a big disadvantage which is evident
from their report [1]. If the central server upon which the
system is running goes down for maintenance, users will
face delays in their transaction which happens very often.
Also, if the central server crashes, all the ongoing transactions
fail and the users have to make the same transactions again.
Moreover, in current digital payment systems, when a user
withdraws money from his E-wallet to the bank account,
some additional amount is deducted. Banks charge this fee

B. Blockchain as a Solution to Digital Payment System
Blockchain technology has received significant attention in
recent years. It is analyzed as a prominent component of nextgeneration e-government [3]. Blockchain is a decentralized
ledger system over a peer to peer network where every node
in the network has the same copy of the ledger. The changes
associated with any node are reflected in every other node
in the network. So, all the changes and updates happen
simultaneously at each node.
Every node in the network stores the database in the form of
a chain of blocks where every block contains a set of changes
or updates associated with the nodes. Every change or update
is referred to as a transaction in the context of this technology.
Blockchain technology has various methods for validating
transactions known as the consensus mechanism. Every transaction over the network is encrypted and it undergoes this
consensus mechanism. So, only verified transactions are added
to the block and then to the blockchain. The data in each
node in the blockchain is immutable. So, it’s not possible to
change data in the blockchain. Even if someone tries to change
the block, the blockchain at that node becomes invalid. Ever
since Blockchain technology has been introduced in 2009,
technology drastically changed with a lot of improvements
in 10 years. Private blockchains have found its application
in many domains outweighing public blockchains. It is so
because its architecture can be designed and enhanced as per
the needs of an organization. So, a decentralized blockchainbased payment system would be ideal for the digital payment
system which would tackle all the issues with centralized and
distributed systems.
C. Istanbul Byzantine Fault Tolerance
Istanbul Byzantine Fault Tolerance (IBFT) is a Proof-ofAuthority (POA) consensus protocol well suited for permissioned networks. This method gives a small and designated
number of blockchain actors called validators, the power to
validate transactions. The consensus mechanism is as follows: One of the validators’ nodes is randomly chosen as
the Proposer and is responsible for building a block. The
Proposer broadcasts that block with other validators at the

block interval. If the block is considered valid by a supermajority of validators, it is added to the blockchain and shared
to other non-validator nodes. Else, the proposer changes and
process starts again. Some of the benefits of IBFT consensus
are:
• Immediate block finality. As there is always one block
that is proposed at an instance and hence uncle blocks
and forking are prevented in the chain.
• Reduced time between blocks. The construction and
validation of block doesn’t involve any computational
effort as with POW based consensus, greatly increasing
the throughput.
• High data integrity and fault tolerance. To ensure
integrity, IBFT uses a majority of 66% validators to agree
with the proposed block which makes it hard for block
forgery. Further, the proposer changes over time which
avoids any faulty node from exerting its influence over
the chain group of validators to ensure the integrity of
each block being proposed.
• Operationally flexible. The validators set can be changed
at any time flexibly, ensuring the group of validators
contains only trusted nodes.

III. P ROPOSED A RCHITECTURE
Limitations of the current digital payment systems are
discussed in Section I-A. An architecture of a private permissioned blockchain-based digital payment system with a
decentralized user database using IBFT consensus is proposed.
The proposed architecture consists of three types of nodes.
First is the user node, which is the user device itself having
an E-wallet. Second is the Bank node, which is a full node
having limited access to the bank’s central database containing
user accounts. These nodes create transactions for transferring
money from banks to E-wallet. The third is the validator node.
These nodes validate the transactions made by the users and
do not create any transaction by themselves. Both bank nodes
and validator nodes are full nodes that store blockchain and
the database containing details of all users registered with the
system. The process of creating an account, consensus, and
making a transaction is discussed in further sub-sections.

C. Integration of Banks with the system
Each of the banks will have a full node which is connected
to the central database of the bank. These nodes, which we
refer to as bank nodes present at the bank have limited access
over user accounts. These nodes will update accounts of users
only after committing a block and if the block consists of
transactions involving bank accounts of the respective users.
The two types of transactions which involve the bank account
of the users are discussed below.
1) Money transfer from E-wallet of user to the user bank
account: Consider the scenario where User A wants to make
a transaction for transferring money from his E-wallet to the
bank account. User A selects his bank to which he wants
to transfer money and enters the amount to be transferred.
The digitally signed transaction is then broadcasted to all the
validator nodes. After the validator nodes commit the block,
the block is forwarded to the bank node. When the bank node
commits the block containing this transaction, it searches for
the user account associated with the public key of User A
present in the transaction and makes the corresponding update
in the bank account of User A. This scenario is shown in

Fig. 3. Algorithm 4 describes how money is transferred from
E-wallet to the bank account.
2) Money transfer from user bank account to the user
E-wallet: When User A wants to transfer money from his
bank account to E-wallet, he makes a request to his bank
node. The bank node then creates a transaction with the
amount to be transferred along with the public key of the
user as the recipient address. The bank node then broadcasts
the transaction to all the validator nodes. After the block is
committed, it is broadcasted to user nodes and bank nodes.
Once the bank nodes and user nodes add the newly received
block to their blockchain, the bank account of user and the Ewallet are updated respectively as shown in Fig. 4. Algorithm
6 describes the process of transferring money from a user bank
account to a user E-wallet.
D. E-wallet app
To use the system, a user has to install the E-wallet app on
his/her device. In general, user devices do not have enough
space to store the entire blockchain. This storage limitation
can be overcome by making this E-wallet app a light node.
Different types of light nodes are proposed in [17]–[20]. A
light node stores the blockchain partially instead of storing the
entire blockchain. It stores the most recent block headers in it.
As an example, we can consider the Simple Payment Verification (SPV). This concept is developed by Satoshi Nakamato
described in the bitcoin whitepaper. Nodes with low storage
can be a participant of blockchain by using SPV and making
payment operations. These nodes cannot verify transactions
by themselves as they only store the block headers, but they
request for content of block from the validator nodes when
required. After receiving the requested block, the light node
uses Merkle-tree to ensure the data integrity of the block. In
this way, even users with low storage can use the system.

V. C ONCLUSION AND F UTURE WORK
A blockchain based architecture for payment systems is
proposed. IBFT consensus greatly increases the throughput in
the system as compared to other POW consensus protocols.
As the blocks committed only after a majority agreement, the
system ensures high integrity and same chain height resulting
in immediate block finality.
The system scales up easily and can achieve an appreciable
speed and performance. As part of future research, we would

investigate how features like private transaction can be utilised
in payment systems. The system is yet to be tested in real time
and variation in performance in different network scenarios
will be analysed.
