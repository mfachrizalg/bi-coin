# Benchmark evidence and statistical study

The primary study uses isolated transaction types and five-run statistics. The
former mixed transaction selector is removed; retail transfers, merchant
payments, queries, and administrative operations are separate Caliper rounds.

Fresh study outputs are captured below `benchmark/results/statistical-<stamp>/`.
Historical `20260909-final-*` files remain reproducibility evidence for the old
run and must not be cited as the new study.

Prerequisite: the five-organization network is up and the `digital-rupiah`
chaincode (v3.0, sequence 1) is deployed on a clean ledger, exactly as for the existing transfer benchmarks
(`npm run benchmark:transfer:w2`). All commands run from `bi-coin-fabric/`.

## 1. Statistical study

Start the full pilot, worker calibration, scenario pilots, and five-repetition
primary sweep with:

```
npm run benchmark:study -- full
```

The phases can be resumed independently:

```
npm run benchmark:study -- pilot
npm run benchmark:study -- calibrate
npm run benchmark:study -- primary
```

The study first pilots low-contention retail transfers, calibrates Caliper at
1, 2, 4, and 8 workers, and selects the smallest worker count that sustains the
highest passing load. That worker count is then fixed for every primary
scenario. Each fixed-rate load uses a fresh ledger and five 120-second
repetitions.

The sustainability gate is declared before result interpretation: every
repetition must achieve at least 99% successful completions and successful-
transaction p95 latency at most 2.5 seconds. Offered TPS is submitted divided
by the measured duration; Achieved TPS is successful divided by that same
duration. Caliper's failure-inclusive `Throughput (TPS)` column is retained
only as a compatibility field, not as Achieved TPS.

The eight report sections are generated by:

```
npm run benchmark:analyze -- benchmark/results/statistical-<stamp>
```

They cover Offered/ Achieved TPS, completion counts, failure reasons, latency
percentiles, saturation, resources, isolated transaction types, and
five-repetition variability.

## 2. Custody authorization and full-suite execution

```
npm run benchmark:authorization
```

`benchmark/workloads/custody-authorization.js` uses explicit Caliper
`invokerMspId`/`invokerIdentity` fields: BI creates the fixture, then Himbara
tries to spend the BI-custodied wallet. The JSON `authorization-oracle` line
must report `verdict=PASS`, a custody error, and zero infrastructure errors.
Endorsement, timeout, and channel failures are invalid negative evidence.

Run the complete evidence sequence with:

```
BENCHMARK_CLEAN_LEDGER=true ./scripts/run-full-suite.sh
```

The suite resets Garuda between profiles, runs boundary and custody
authorization checks, and writes a schema-v2 manifest containing artifact
SHA-256 hashes, Caliper/runtime versions, and the clean-ledger/chaincode
version/sequence precondition. `scripts/network-down.sh` removes Docker
volumes only when `NETWORK_DOWN_REMOVE_VOLUMES=true` is explicitly set.

Workload: `benchmark/workloads/negative-path.js`. Every submission violates one
policy rule (per-transaction cap, insufficient balance, receiver max-balance,
frozen sender, expired KYC, prohibited-risk approval, high-risk approval without
senior sign-off) and must be rejected.

Read the `[negative-path] worker N: rejected_status=.../..., gaps=...` lines at the end.
`gaps=0` on every worker means each rule rejected as required. Because rejection
is the intended outcome, Caliper's own report counts these as failed transactions;
that is expected — the verdict is the enforced/gap summary, not the success ratio.

Paper use: replace the standalone "zero policy or limit rejections" framing with a
negative-path conformance table (rule -> expected vs observed rejection). This
turns "nothing was rejected" into "every rule rejected exactly the disallowed
input."

## 3. Adversarial double-spend — tests the MVCC claim under contention

```
npm run benchmark:adversarial
```

Workload: `benchmark/workloads/adversarial-double-spend.js`. All four workers
transfer from one shared sender wallet, so concurrent transfers read the same
balance version. Fabric MVCC commits one per block and rejects the rest.

Read `[overspend-contention] worker N: committed=..., rejected=...`. A nonzero aggregate
`rejected` under contention is the evidence that concurrent same-wallet spends are
rejected "even after passing the balance check." If `rejected` is 0, increase
`workers` / `tps` in `benchconfigs/adversarial.yaml` until submissions overlap
within a block.

Paper use: report the committed/rejected split as the adversarial test the current
Limitations section says is absent.

## 4. Repetition and contention

```
npm run benchmark:transfer:repeat
```

The statistical study reports both low-contention and deliberate
high-contention retail-transfer scenarios. Low-contention plans lease disjoint
wallet pairs; high-contention plans share a funded sender so MVCC behavior is
observable without intentionally exhausting the balance. Every confirmatory
load is repeated five times and reports mean plus sample standard deviation.

## 5. Resource metrics — localizes the throughput bottleneck

All benchconfigs previously used the Caliper 0.4 monitor schema
(`monitor: {type: docker, docker: {name: [...]}}`). Caliper 0.6 reads
`monitors.resource[].module` (`monitor-orchestrator.js:42`), so the old block was
silently ignored and every run logged `No resource monitors specified`. No CPU,
memory, network, or disk data was ever collected.

All benchmark configs now use the 0.6 schema and monitor all 11 containers (5 peers,
5 CouchDB instances, the orderer). The previous list omitted every CouchDB
container, which is the prime suspect for the commit-path bottleneck.

Each run now also produces a resource table per container: Memory(max),
Memory(avg), CPU%(max), CPU%(avg), Traffic In, Traffic Out, Disc Read,
Disc Write.

The refreshed study starts the pinned Prometheus/cAdvisor/node_exporter stack.
It records per-container CPU, memory, network I/O, disk bytes, IOPS, and
derived read/write service time, together with host CPU, memory, disk, and
network metrics. Caliper's process monitor records the client process.

The primary Fabric study excludes API and PostgreSQL latency. PostgreSQL/KYC is
measured separately with:

```
bash scripts/run-kyc-e2e.sh
```

That demonstration runs five authenticated HTTP onboarding flows through the
real PostgreSQL store and Fabric gateway, and reports per-step mean and sample
standard deviation. It is not combined with Fabric throughput or saturation.

## 6. Results

Caliper writes an HTML report, full log, generated configuration, and raw
transaction trace for every study run. Prometheus responses are retained in the
same run directory; completed Prometheus JSONL is losslessly gzip-compressed as
`prometheus.jsonl.gz` when storage is constrained. `summary.json`, CSV tables,
`REPORT.md`, and the manifest are derived from those raw artifacts.

KYC and wallet-tier rejection evidence belongs in the technical appendix and
is classified separately from expected negative-path scenario verdicts.
Cross-border interoperability is outside this benchmark.

Keep the June 30, July 27, August, and September pre-study result files as
historical artifacts only.
