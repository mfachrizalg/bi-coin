# Backend and chaincode correctness review

> **Four-organization restatement (2026-10-16):** five-organization evidence in this document is superseded by the four-organization network (CentralBankMSP, DistributorMSP, ValidatorMSP, EndUserMSP). The role `validator_bank` and participant type `validator` were removed; banks are `distributor`. Terms are kept as recorded at review time and are not evidence for the four-organization prototype.

Scope: the current backend and Fabric chaincode, checked against the repository glossary, ADRs, focused Go LSP diagnostics, current Fabric read/write semantics, and the existing tests. QRIS-specific defects are deferred because the user chose to disable the feature. Captured benchmark results and historical ledger records were preserved.

The pre-change suites passed 154 backend tests and 58 chaincode tests. Those suites did not model Fabric's committed-state reads correctly and did not cover the failure cases below.

Post-change verification: backend 169/169 and chaincode 61/61 pass; both `-race` suites pass; Go LSP reports no diagnostics for changed Go files; frontend contract tests pass 13/13 and the production build succeeds; benchmark script tests pass 51/51. The Garuda Fabric network now runs chaincode v5.0 sequence 3 with Bank Indonesia, Distributor Bank, Distributor Bank B, and PJP approvals; sequence 1 was not reset. Fabric queries confirm `PayQris` and `GetAutoLimitPolicy` are not exposed, `GetTotalSupply` remains zero, and `GetOperationReceipt` is available. The original local chaincode package archive was restored unchanged.

The browser login smoke test was not run: starting the backend against its configured `localhost:5433` PostgreSQL endpoint failed because that port refused the connection. The active Fabric peers do not provide a running backend service.

| Priority | Finding and evidence | Disposition |
|---|---|---|
| P1 | `chaincode/digital_rupiah.go` (`settleTransfer`/`autoRedeem`) could redeem a retail remainder after the transfer write. Fabric `GetState` returns committed state, so the helper reread the original balance and overwrote the pending debit, creating value while recording a burn. Bank Indonesia's PoC describes automatic redemption for wholesale liquidity above a participant maximum; its minimum threshold instead triggers automatic issuance. | Removed the retail low-balance trigger, policy API, and admin-policy benchmark. Explicit BI-authorized redemption remains. |
| P1 | `chaincode/digital_rupiah.go` (`CreateWallet`) replaced a failed active-Custodian lookup with the retail owner's ID. This left an unfrozen wallet outside later Custodian lifecycle checks. | Wallet creation and new transfers require an active Distributor/PJP Custodian; lookup failures propagate. Historical wallet records were not rewritten. |
| P1 | `backend/services/ledger.go` (`beginOperation`) rejected any pending journal entry. A timeout or crash after commit could leave an operation permanently unrecoverable. | Retries query ledger receipts, then reuse the same reference if no receipt exists. Journal transitions cannot move backward. |
| P1 | `backend/services/ledger.go` (`PayQris`/`ResolveQrisPayload`) and QRIS state updates keyed payments per payer, so competing payers could debit separately; expiry could mask a committed payment. | QRIS routes, UI controls, the dashboard panel, and exported `PayQris` are commented out. Source and data remain. Receipt-bound single-payment and expiry recovery are prerequisites for restoration. |
| P2 | `chaincode/digital_rupiah.go` (`settleTransfer`, `RequestIssuanceRtgs`, `DistributeToParticipant`) returned receipts before checking payload and caller custody. | Replay paths authorize the caller and compare immutable fields, including integer amounts decoded without floating-point conversion. |
| P2 | Backend issuance/redemption handlers and chaincode `RequestIssuance`/`RequestRedemption` lacked durable REST idempotency. | Both endpoints require `Idempotency-Key`; receipts bind each reference to its amount and participant/wallet. Redemption is BI-only. |
| P2 | `backend/services/ledger.go`/`postgres_store.go` (`SubmitKycProfile`) generated a new profile ID after an anchor failure. The upsert could overwrite approval and clear the anchored flag. | Profile IDs derive from the operation reference; chaincode receipts make anchoring retryable, and PostgreSQL inserts preserve the existing review. |
| P2 | `backend/services/auth.go` (`AuthService.Verify`) allowed old JWT claims after same-role subject, participant, or Custodian reassignment. | Token verification compares all three claims to the current user record. |
| P2 | `chaincode/digital_rupiah.go` (`GetTransactionHistory`) compared participant IDs with transaction wallet IDs, so scoped queries missed participant activity. | History resolves wallets bound to that participant before applying existing filters. |

The confirmed Fabric behavior behind the first finding is documented in [Fabric's read/write-set semantics](https://github.com/hyperledger/fabric/blob/main/docs/source/readwrite.rst): reads after writes return committed state; read-your-writes is not supported. Bank Indonesia's [December 2024 Project Garuda PoC report](https://www.bi.go.id/id/rupiah/digital-rupiah/Documents/Laporan_POC_Proyek_Garuda_ID.pdf) describes wholesale auto-redemption above a participant's maximum balance and auto-issuance below its minimum balance.
